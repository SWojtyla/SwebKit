- app.css is patch-fragile once theme work is in flight; prefer small targeted apply_patch edits over large multi-hunk patches, and re-read the exact selector block before patching when line drift is likely.
- tests/SwebKit.E2E.Tests/AppFixture can attach to an already-running WebView2/CDP app session; do not trust theme-reset assertions unless the app was relaunched into a fresh session.
- SwebKit.App.Tests.csproj manually lists every <RazorComponent> item. Adding a new .razor file to src/SwebKit.App/Components/Storage/ requires a matching entry in the test project .csproj or the component class will not be found in tests (CS0246).
- Shell-local pages that read UiStateRepository on initial route render should wait for or react to AppStateService.Initialized before saving, because UiState.LoadAsync runs during MainLayout background initialization.
- SwebKit.App.Tests.csproj's manually-curated <RazorComponent>/<Compile> include list applies to ANY component referenced from a test, not just newly-created ones — an existing, unmodified .razor file (e.g. BasicAuthForm.razor, KeyValueGrid.razor) will still fail with CS0246 in a new test file until it's added to that list.
- Many SwebKit.App.Tests classes construct `new UiStateRepository()` directly, which writes to the real shared `%AppData%\SwebKit\ui-state.json` (no per-test isolation) unless the test explicitly overrides `SWEBKIT_APPDATA_ROOT` (see MessageComposerTests/TemplatePickerTests/ScheduledMessagesComponentTests/PinnedPortForwardServiceTests for that pattern). `[Collection("AppDataSerial")]` only serializes tests _within_ that collection against each other — test classes outside it (e.g. CommandRegistryTests, AlertMonitorServiceTests) can still race concurrently-running "AppDataSerial" tests on the same physical file, surfacing as `IOException`/`UnauthorizedAccessException` from `AppDataFileStore.SaveAsync`'s `File.Replace`/`File.Move`. `AppDataFileStore.SaveAsync` now retries transient failures (~8 attempts, short backoff) as a blast-radius mitigation, but the real fix is auditing all `new UiStateRepository()` test call sites to either join "AppDataSerial" or use the `SWEBKIT_APPDATA_ROOT` temp-dir override.
- `dotnet test --collect:"XPlat Code Coverage"` on SwebKit.App.Tests produces a Cobertura report with NO `SwebKit.App` package by default — root cause found and fixed: SwebKit.App.Tests can't ProjectReference the MAUI-targeted SwebKit.App head project, so it source-links a curated subset of .razor/.cs files directly into the test assembly instead (see the RazorComponent-whitelist note above). That means the real component code physically lives inside SwebKit.App.Tests.dll, and coverlet excludes the test assembly from coverage by default — so none of it was ever measured. Fixed by adding `tests/SwebKit.App.Tests/coverlet.runsettings` with `<IncludeTestAssembly>true</IncludeTestAssembly>`; run coverage with `--settings tests/SwebKit.App.Tests/coverlet.runsettings`. With that fix, real frontend coverage (SwebKit.App.Components/.Services/.Models classes only, excluding the SwebKit.App.Tests.\* test classes themselves) is ~51% — reasonable, not the "0%/unmeasured" it looked like before. Worst folder: `Components/Monitoring` at 0% across 25 classes.
- SwebKit.Core's real coverage is NOT reflected by running SwebKit.App.Tests alone (that only exercises Core incidentally, diluted by unrelated low-coverage packages like SwebKit.Azure/Kubernetes in the same aggregate). Run `SwebKit.Core.Tests` directly for the true number: ~66.7% line coverage — much healthier than the ~14% aggregate. Real, non-demo/mock gaps worth closing: `Services/BrunoFolderImporter.cs` (511 lines, 0%), `Services/GraphQlSubscriptionService.cs` (157 lines, 0%), `Configuration/LinkedCollectionRootRepository.cs` (64 lines, 0%), `Services/PortForwardSessionService.cs` (44 lines, 0%), `Services/WebSocketClientService.cs` (30%), `Services/CollectionImportService.cs` (8.6%). The other 0%-coverage files (`DemoApiCollectionFactory.cs`, `DemoDevOpsClient.cs`, `DemoStorageClient.cs`, etc.) are demo/mock-data generators — low risk, low priority.
