API Client request runs

Dependency chains ("run this before me") plus ordered batches (folder order or a multi-selection), executed server-side and streamed to the UI over SSE. Single-request Send stays the default; chains are opt-in per send.

The two primitives

All three entry points produce the same thing: an ordered plan of request refs. Folders order by tree position; multi-select preserves tree order too — no saved-sequence entity in v1.

Run flow

What a step failure means

A step fails on transport error or HTTP status ≥ 400 — chains asserting happy paths should stop when a 500 shows up. With stopOnError (default on) the run emits stepFailed then aborted; with it off the run continues and done reports failedSteps.

Why it holds up

Reuses the executor

Each step goes through the same env resolution, auth injection, and capture pipeline as /execute — chains inherit token capture for free, and behavior can't drift between "send one" and "run many".

No new entity

Batches come from tree order and selection, not a persisted "sequence" object — nothing new to sync, conflict, or migrate on either storage origin. Deps ride inside the request file they belong to.

Plan before stream

Cycles, missing deps, and oversize plans fail as a normal 400 before the SSE stream opens — the UI shows an error toast, never a dead drawer.

Origin-agnostic

Runs resolve collections the same way /execute does — internal, linked root, or demo — so chains work identically on Bruno-style folders and AppData collections.

Trade-offs & v2 runway

  • Sync-per-step execution: steps run strictly in order — parallel groups are a v2 candidate. Within a run, order is the point.
  • Same-collection deps only: cross-collection chains would tangle env scoping; rejected at plan time with a named error.
  • No named sequences yet: the run contract (explicit mode) already accepts caller-supplied order, so saved sequences slot in later as a persisted list — no protocol change.
  • 25-step cap: bounds runaway transitive closures; bump or paginate later if real use needs it.
  • Demo parity: a chained demo pair makes the feature exercisable and e2e-testable without a live API.
