One design system for both apps

SwebFlow was redesigned as SwebOS: a real design system — semantic tokens, a fixed state vocabulary, in-house primitives, two theme families (Aurora cool indigo, Clay warm terracotta) × light/dark. These mocks render SwebKit's three heaviest pages in that system, inside the SwebOS shell. Adopting it makes the apps visibly related and lets SwebKit drop 5 of its 9 themes. Nothing is wired — mock data only. Use the switcher (bottom-right) to flip family + mode.

The heaviest page: spec shell + 232px nav, the adopted resource rail, a live pods table using the six-state vocabulary (Running → done, Pending → waiting, CrashLoopBackOff → blocked), and the pod detail rail with the shared log syntax palette.

What changes

  • Chrome — sidebar 224 → 232px, topbar 48px, status bar removed (health folds into a topbar dot + System popover, per spec §8).
  • Tokens — every colour goes through the semantic set (--surface-1/-2/sunken, --text/-muted/-subtle, --accent/-ink/-soft, --border/-strong) plus the six --state-* triplets.
  • Type scale fixed — 12/13/14/16/20/24 only; section labels sentence-case, no uppercase tracking.
  • Primitives — one Button (primary/secondary/ghost/danger × 28/32), Card, Chip, StateBadge, Tabs, DataTable. Radius & elevation come from the family, not per-page choices.
  • Sizing — control 32/28, table row 36, right rail 360, nav row 32.

What stays

  • Layout of each feature — AKS keeps its rail + table + detail panel; API Client its tree/editor/response; Service Bus its ribbon groups + tree + list. This is a skin + system adoption, not a redesign of the tools.
  • Feature vocab — DLQ, peek, resubmit, port-forward, capture rules… nothing renamed.
  • Log/YAML/JSON syntax palette — SwebOS already ships the shared --cm-* token set both apps use.
  • Mono identifiers — pod names, message IDs, SHAs stay mono; spec keeps identifiers off the accent colour.

Open questions to judge on the mocks

  • Family — Aurora only, Clay only, or ship both like SwebOS? (Switcher is on every mock.)
  • Density — spec fixes rows at 36px and controls at 32. Current SwebKit is tighter. The mocks run spec density; if it feels too airy for a tool, that's a spec amendment, not a per-theme thing.
  • Status bar — spec has no footer. Keep SwebKit's health strip anyway, or adopt the topbar dot + popover?
  • Ribbon — Service Bus keeps its four action groups but as spec tabs (mock shows Messages). Alternative: keep the literal ribbon, restyled. Decide after seeing it.
  • Accent on identifiers — spec bans accent colour on IDs/links-as-data; names stay text + mono, accent stays a signal.
